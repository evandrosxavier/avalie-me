Resumo

Este relatório documenta o projeto avalie-me, uma plataforma serverless de feedback de cursos hospedada na Microsoft Azure. A solução foi construída inteiramente em Java puro, sem framework, sobre Azure Functions (modelo FaaS), atendendo aos requisitos da Fase 4 do Tech Challenge da FIAP: ambiente de nuvem seguro e monitorado, deploy automatizado, notificação imediata de avaliações críticas e relatório semanal com média de avaliações. O documento cobre arquitetura, regras de negócio, contrato da API, segurança e governança de acesso, modelo de dados, instruções de configuração e execução, e o guia de testes.

1. Introdução

1.1. Descrição do Problema

Para garantir a qualidade dos cursos on-line, é essencial que os estudantes possam fornecer feedback e que os administradores possam acompanhar rapidamente a satisfação dos alunos. O sistema precisa receber feedbacks, notificar imediatamente os administradores sobre itens críticos e gerar relatórios periódicos para análise dos dados — tudo isso em um ambiente de créditos de nuvem limitados, o que empurra a arquitetura para o modelo serverless: paga-se apenas pelo que é executado.

1.2. Objetivo do Projeto

Desenvolver uma aplicação hospedada em nuvem, com funções serverless para automatizar:

  • O recebimento e a validação de feedbacks de alunos;
  • O envio de notificação imediata ao administrador quando a avaliação for crítica (urgência ALTA);
  • A geração de um relatório semanal consolidado, com média de avaliações e distribuição por urgência.

1.3. Escopo

O sistema é composto por três Azure Functions independentes, cada uma com responsabilidade única:

FunçãoTriggerResponsabilidade
ingestHTTPRecebe, valida e persiste a avaliação; publica na fila se urgência ALTA
notifyQueueEnvia e-mail de aviso ao administrador e grava auditoria de notificação
reportTimerGera e publica o relatório semanal, envia o link por e-mail

2. Arquitetura do Sistema

2.1. Descrição da Arquitetura

A solução adota o modelo FaaS — Functions as a Service, a forma mais granular de serverless: não há sistema operacional, runtime ou servidor lógico para gerenciar — o código "acorda" a cada evento (chamada HTTP, mensagem na fila, disparo do timer) e a cobrança é apenas pela execução. As três funções rodam no mesmo Function App, sob o plano Consumption, e se comunicam de forma assíncrona via Storage Queue para o caminho de notificação.

Cada função é implantada como parte do mesmo artefato Java, mas mantém isolamento de responsabilidade: ingest é o único ponto de entrada externo de escrita; notify e report são consumidores/produtores reativos, sem acoplamento direto com quem os invoca.

3. Regras de Negócio

3.1. Validação em Duas Camadas

Toda avaliação passa por duas camadas de validação independentes, seguindo o princípio de defesa em profundidade:

  • Entrada (IngestFunction): barra estrutural — presença dos campos, tipo correto, JSON bem formado;
  • Domínio (AvaliacaoService): reforça a mesma checagem e aplica a regra de negócio — nota entre 0 e 10, descrição com no mínimo 15 caracteres.

A camada de domínio replica a validação estrutural mesmo que pareça redundante: protege o serviço contra chamadores futuros que eventualmente pulem a borda HTTP.

Em ambas as camadas os erros são acumulados, não interrompidos no primeiro problema: uma requisição sem nota e sem descricao devolve os dois erros na mesma resposta. A camada de domínio agrupa os erros na exceção ValidacaoException, que os transporta até a borda HTTP como lista.

3.2. Derivação de Urgência

NotaUrgência
0 – 3ALTA
4 – 6MEDIA
7 – 10BAIXA

A urgência é derivada automaticamente pela função Urgencia.deNota(int nota) — nunca informada pelo cliente. Apenas avaliações ALTA disparam o fluxo de notificação imediata.

3.3. Imutabilidade da Avaliação

Uma avaliação, uma vez registrada, não se altera. Não existe endpoint de atualização ou exclusão. Essa regra se reflete em três camadas: o record Avaliacao é imutável por natureza; a persistência usa createItem (falha em vez de sobrescrever um id repetido); e o repositório não expõe nenhuma operação de update.

3.4. Fluxo dos Dados

  1. Aluno envia POST /avaliacao com descrição e nota;
  2. ingest valida, deriva a urgência e persiste no container avaliacoes do Cosmos DB;
  3. Se urgência ALTA, ingest publica uma mensagem na fila avaliacoes-urgentes;
  4. notify é acordada pela fila, envia e-mail ao administrador e grava o resultado no container notificacoes;
  5. Toda segunda-feira às 8h (horário de Brasília), report consolida os dados da semana civil anterior fechada — de segunda 00:00 ao domingo 23:59:59, no fuso de São Paulo — em um relatório HTML publicado no Blob Storage.

4. Notificação Assíncrona

4.1. Infraestrutura

ComponenteNomePapel
Storage Queueavaliacoes-urgentesFila principal, consumida pelo notify
Poison Queueavaliacoes-urgentes-poisonMensagens que esgotaram as 5 tentativas de retry

A fila é declarada via @QueueOutput (produtor, em ingest) e @QueueTrigger (consumidor, em notify), usando a mesma connection string AzureWebJobsStorage do runtime.

4.2. Payload da Mensagem (bilhete gordo)

{
  "id": "35bd4e32-7b4b-4cb9-bc1d-acfb036edf67",
  "descricao": "Plataforma travou durante o exercicio final",
  "nota": 2,
  "urgencia": "ALTA",
  "dataRegistro": "2026-07-25T02:24:51.273993564Z"
}

A mensagem já contém todos os dados que o notify precisa — desenho event-carried state transfer — evitando uma consulta extra ao Cosmos DB no consumidor.

4.3. Snapshot de Auditoria

Cada tentativa de envio gera um documento Notificacao no container notificacoes, com histórico append-only (uma tentativa nunca sobrescreve a anterior):

avaliacaoId · descricao · nota · urgencia · dataRegistroAvaliacao · dataEnvio · status (ENVIADO | FALHA)

4.4. Retry e Poison Queue

Se o envio de e-mail falhar, o NotifyFunction grava a Notificacao com status FALHA e relança a exceção — isso aciona o retry nativo do Azure Functions (5 tentativas com backoff). Se todas as tentativas falharem, a mensagem é movida automaticamente para a fila de poison, disponível para inspeção manual sem perda de dados.

5. Segurança e Governança de Acesso

5.1. Segredos no Key Vault

COSMOS_CONNECTION_STRING e ACS_CONNECTION_STRING não ficam em texto puro nas configurações do Function App — são referenciadas via @Microsoft.KeyVault(SecretUri=...) e resolvidas em runtime a partir do cofre kv-avalieme-dev.

5.2. Managed Identity

O func-avalieme-dev acessa o Key Vault por meio de uma identidade gerenciada atribuída pelo sistema (system-assigned Managed Identity) — nenhuma credencial fixa é armazenada em lugar nenhum. A política de acesso concede apenas permissão de leitura de segredo, seguindo o princípio de menor privilégio.

5.3. Rotação de Chaves

A chave do Cosmos DB foi regenerada logo após a migração para o Key Vault. A AccountKey da Storage Account também foi renovada quando exposta acidentalmente em uma sessão de terminal durante o desenvolvimento — prática de resposta a incidente aplicada de forma proativa.

5.4. Erros Estruturados (RFC 9457)

Toda resposta de erro do ingest segue o formato application/problem+json, sem vazar detalhes internos ao cliente. Quando há mais de um problema na mesma requisição, todos são reportados juntos: o detail traz o resumo e o campo errors lista cada erro individualmente.

{
  "type": "https://github.com/evandrosxavier/avalie-me/erros/validacao-entrada",
  "title": "Erro de Validação",
  "status": 400,
  "detail": "Requisição inválida: nota é obrigatória; descricao é obrigatória",
  "instance": "/avaliacao",
  "errors": ["nota é obrigatória", "descricao é obrigatória"]
}

O campo errors é omitido quando não há lista aplicável — corpo da requisição ausente ou JSON malformado.

StatusQuando
400Payload estruturalmente inválido, ou violação de regra de negócio
500Falha inesperada (ex.: indisponibilidade do Cosmos DB), sempre capturada por catch-all

5.5. CI/CD com Menor Privilégio

O deploy automatizado autentica-se via service principal escopado apenas ao resource group rg-avalieme-dev, armazenado como secret do repositório (AZURE_CREDENTIALS) — sem acesso a outros recursos da assinatura.

5.6. Blob Storage Público — Escopo Restrito

O acesso público de leitura é restrito ao container relatorios (necessário para o link do relatório funcionar sem autenticação). Os demais containers, incluindo a fila de mensagens, permanecem privados.

7. Relatório Semanal

7.1. Trigger e Periodicidade

TriggerTimerTrigger
Cron0 0 11 * * MON (UTC) — toda segunda-feira, 8h horário de Brasília
Janela de dadosSemana civil anterior fechada: de segunda-feira 00:00 ao domingo 23:59:59, no fuso America/Sao_Paulo

A janela é ancorada no calendário, não no instante da execução. O cálculo vive em JanelaSemanal.semanaAnteriorA(...): a partir da data de referência, recua até a segunda-feira da semana corrente e devolve a semana imediatamente anterior. O dia da execução nunca entra no recorte.

O filtro por período é aplicado diretamente na consulta ao Cosmos DB (listarPorPeriodo), comparando o campo dataRegistro (texto ISO-8601, lexicograficamente ordenável) com início inclusivo e fim exclusivo (>= @inicio AND < @fim) — de modo que nenhum registro seja contado duas vezes nem se perca na fronteira entre duas semanas, e o período anunciado no cabeçalho corresponda exatamente aos dados incluídos.

Consequência prática: como a janela não depende do horário do disparo, reprocessar o relatório manualmente em qualquer dia da semana produz exatamente o mesmo documento.

7.2. Conteúdo do Relatório

  • Cabeçalho com o período coberto (segunda a domingo da semana anterior);
  • Cartões de resumo: total de avaliações, média das notas, contagem por urgência (com cor);
  • Gráfico de barras — avaliações por dia;
  • Tabela de avaliações: descrição, nota, urgência (badge colorido) e data;
  • Legenda com os intervalos de nota que definem cada urgência.

O HTML é publicado no Blob Storage com acesso público de leitura, e o link é enviado por e-mail ao administrador via ACS. O YYYY-MM-DD do nome do arquivo é a data do domingo que fecha a semana coberta:

https://funcavaliemedev65741.blob.core.windows.net/relatorios/relatorio-YYYY-MM-DD.html

7.3. Dados para o E-mail de Aviso de Urgência

Conforme especificado no enunciado do desafio, o e-mail de notificação imediata contém: descrição, urgência e data de envio.

7.4. Dados para o Relatório Semanal

Conforme especificado no enunciado: descrição, urgência, data de envio, quantidade de avaliações por dia e quantidade de avaliações por urgência — todos presentes no relatório gerado.

9.3. Deploy Manual

mvn clean package azure-functions:deploy
Armadilha conhecida: o goal azure-functions-maven-plugin:deploy sozinho apenas empacota o que já está em target/, sem recompilar. Rodar só mvn azure-functions:deploy após alterar código publica silenciosamente o jar antigo, sem erro — sempre usar mvn clean package azure-functions:deploy.

9.4. Deploy Automatizado

O repositório possui um workflow do GitHub Actions (.github/workflows/deploy.yml) com disparo manual (workflow_dispatch), autenticado via service principal. A escolha por disparo manual — em vez de gatilho automático a cada push — é deliberada: evita consumir créditos de cloud limitados durante o desenvolvimento; o processo de build, empacotamento e publicação em si é inteiramente automatizado pela pipeline, sem passos manuais.

  1. Avaliação normal: POST /api/avaliacao com nota alta → confirmar 201 e urgência BAIXA;

11. Monitoramento

O Application Insights (appi-avalieme-dev) coleta automaticamente a telemetria das três funções via variável APPLICATIONINSIGHTS_CONNECTION_STRING — nenhuma mudança de código necessária. Todas as funções emitem logs estruturados via context.getLogger(), visíveis em:

  • Portal Azure → Application Insights → Logs → traces;
  • Portal Azure → Function App → Functions → [nome] → Monitor.

Consulta útil no Log Analytics:

traces
| where timestamp > ago(1h)
| order by timestamp desc
